# Output note templates

Four notes make up a complete run. `build_catalog_notes.py` generates #2 and
#3 mechanically; #1 and #4 are written by you (judgment work). All notes are
markdown with YAML frontmatter (`date`, `title`, `tags`, `url`); if the
output directory belongs to an Obsidian vault or a repo with its own
frontmatter conventions (check for a CLAUDE.md), follow those instead, and
cross-link the notes with `[[wikilinks]]`.

## 1. Event agenda note (`<slug>-agenda.md`)

Week-at-a-glance + experiences, from the event's experience page:

```markdown
# <Event> — Agenda
Scraped from <url> on <date>. <City, venue, dates>.
Related: [[catalog note]] · [[focus note]] · [[faq note]] · [[my agenda]]

## Week at a glance
### <Day, date> — one ### per day, a |Time|Activity| table per day

## Experiences
### <one ### per experience block, full description text>
```

## 2. Session catalog note — generated by `build_catalog_notes.py`

Summary tables (activity types, tech tracks, top products) + per-type
compact listing. Don't hand-edit; regenerate on refresh.

## 3. Product focus note(s) — generated with `--product "<tag>"`

Full abstracts + speakers for every session carrying a product tag. Generate
one per product the user's profile centers on (e.g. their main product, or
the event's flagship like IBM Bob).

## 4. Personalized agenda note (`<slug>-my-agenda.md`)

The deliverable. Structure that proved to work:

```markdown
# <Event> — My Personalized Agenda
<How it was built: profile source, chosen focus areas, cert picks.>

> ⚠️ If times_published is false: state clearly that day placement is a
> plan, not a schedule, and list the re-run instruction.

<Session lengths line: Breakout 45 · Talk 20 · Lab 90 (verify per event).>

## <Day> — <theme>            (one section per day, incl. arrival day)
| When | Activity |           (fixed anchors + picks with code, title, why)

## Track tallies              (picks per interest cluster — shows coverage)
## Alternates                 (ranked, with the swap reason per entry)
## To do                      (calendar blocks now; favorites + clash check
                               when schedule publishes; cert seat booking)
```

Slot budgeting that matched reality: conference days have ~4.5h of session
time (minus general sessions and lunch); a lab eats two breakout slots; keep
1–2 slots/day unplanned for expo/networking; put alternates next to every
contested slot. Certification exams: check how many free attempts the pass
includes (FAQ) and schedule them at low-conflict moments (pre-conference day,
late afternoon).

### Champion layer (file-first, ask-fallback)

If the user is an IBM Champion, first look for the champion-schedule file
(`assets/champion-schedule.md` in the skill directory, or the same filename
next to the output notes). It is distributed separately, to Champions only.
When present without its `PLACEHOLDER` marker, its per-day entries are fixed
anchors that outrank regular sessions — use them directly, don't re-ask.
Otherwise ask the user to list their commitments (arrival/welcome events,
champion programming blocks, dinners, feedback sessions). Do not assume or
invent champion schedule details — they come from champions-only
communications the user has and you don't.

## 5. FAQ note — generated by `parse_faq.py`

One `###` per question. Regenerate on refresh; answers change (pricing tiers,
deadlines).

## Refresh runs

A refresh = re-scrape + regenerate #2/#3/#5 + diff against the previous
`sessions_raw.json` (keep it next to the notes):

- sessions added/removed/retitled → mention in the summary, update picks if
  a pick disappeared
- `times_published` flipped true → the big one: map every pick and alternate
  to its actual slot, find clashes, resolve via alternates, and rewrite the
  personalized agenda's day tables with real times
- price/deadline changes in FAQ → call out

Never silently regenerate the personalized agenda: it contains user
decisions. Update it in place, list what changed, and re-ask only the forks
that the new data actually reopened.
